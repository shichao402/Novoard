# ADR-0005: 定义时判断，路由只查表

- 状态：Accepted
- 日期：2026-10-12
- 讨论来源：2026-10-09 契约路由纪律讨论链（e5→e9）。用户对初版纪律句"重量决定待遇"的纠正定型了最终表述。

## Context

全系统 A2A 通用语确立后，每条消息走哪个车道（A2A task / ops 旁路）、领什么待遇（持久化、审批门）需要一个判据。讨论中判据换了四代：网络位置 → 传输方向 → 词性（动词/名词）→ 重量（轻命令/重流程）。每一代都有灰区（"同步配置"是动词还是状态，两派能吵），而灰区对路由是致命的：事后必须能干净回答"这条消息为何走这道"，答案应是查定义，而不是复现一个判断器的逻辑。

## Decision

判断在定义时做完，且只做一次；路由不判断，只查表。

具体而言，判断发生在 target / 消息类型被定义的那一刻，语义问题（做事还是报状态？需审计吗？需审批吗？）的答案落成契约字段；运行时路由器只做查表转发，无语义分析、无"看起来像什么"：

| 定义字段 | 运行时行为 |
| --- | --- |
| 定义为 skill（出现在 Agent Card） | A2A 车道，建 task |
| 定义为 ops 帧类型（ping/telemetry/card.update） | 旁路车道，不进 task 状态机 |
| `audit: none / summary / full` | 持久化待遇 |
| `requiresApproval: true` | input-required 审批门 |
| 不在任何注册表 | 拒绝，不路由 |

这是操作系统教科书 policy/mechanism 分离的应用：mechanism（查表转发）留代码，policy（归属与待遇）以数据形式存在定义里。业界同款纪律：HTTP 语义由 method + endpoint 定义决定；gRPC 靠 proto 定义路由；K8s API server 拒绝未注册 kind；HelloKnightTasker ADR-0038 的截止策略物化查表是同一模式（复杂推导在定义时穷举物化，运行时 O(1)）。

动词/名词、轻重这类启发式不消失，只换岗：

1. 定义时 checklist：新消息类型诞生时，用它决定该定义成 skill 还是 ops 帧。
2. 定义 lint：review 时检查"纯状态描述却被定义成 skill 会制造 task 噪音"这类问题。

从此不出现在运行路径上。

## Consequences

- 收益：路由行为无灰区、可解释（查定义即可回答）；演化安全（新增通道归属是显式契约变更，过 review 有版本，行为不可能悄悄漂移）；Agent Card 的 skill 清单即远程执行白名单，能力声明模型与安全模型天然重合。
- 代价：每个新 target / 消息类型定义时要多回答几个字段问题；契约 schema 需要维护并作为两仓 SSOT。
- 替代方案否决：任何形式的运行时语义判断（按词性、按重量、按"看起来像"）——灰区不可证明完备，事后审计不可解释，演化时行为漂移不可控。
